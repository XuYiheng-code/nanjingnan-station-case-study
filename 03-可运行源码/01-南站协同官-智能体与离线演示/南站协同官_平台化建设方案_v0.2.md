# 南站协同官：平台化建设方案 v0.2

## 这次调整的判断

数字鲜笋营的导师团智能体给出的关键启发，不是“做一个更漂亮的聊天页面”，而是把一套已有的研究资产变成可持续使用的工作环境：用户有明确入口，知识材料有独立位置，任务会留下过程记录，最后还能导出成果。

南站协同官也应按这个思路推进。它不应停在 SC-01 的单次演示上，而应成为南京南站案例研究的工作平台。SC-01 保留，但只作为“协同实验室”的一个情景。

## 对标关系

| 数字鲜笋导师团 | 南站协同官平台 |
| --- | --- |
| 导师包、案例库、方法材料 | 案例包：来源登记、证据卡、权责规则、模拟情景 |
| 单导师对话、六人会审等工作模式 | 案例项目、证据审阅、协同推演、案例复盘等工作模块 |
| 研究档案与右侧活文档 | 可回看的案例项目和活动记录 |
| 导师意见与研究文档导出 | 协同议题卡、证据链、确认记录与案例材料导出 |
| 置信度徽标与不编造约束 | 来源、审批状态、数据状态与人工确认门槛 |

两者的智能体逻辑不同。数字鲜笋的核心是“多位导师的判断差异”；南站协同官的核心是“不同主体之间的证据、权限和确认关系”。因此不能照搬人物复刻或聊天界面，而要复用其平台结构和资产沉淀方式。

## 平台结构

```text
案例包（可替换）
  ├─ 来源登记 source registry
  ├─ 已批准证据卡 evidence cards
  ├─ 权责规则 authority rules
  └─ 情景与事件 scenarios
             │
平台内核
  ├─ 案例项目 project
  ├─ 活动记录 activity trail
  ├─ 人工确认 human gate
  └─ 审计记录 audit log
             │
用户模块
  ├─ 案例项目工作台
  ├─ 证据与边界库
  ├─ 协同实验室
  └─ 案例叙事与复盘（下一阶段）
```

“案例包”与平台内核分开，是后续复用的前提。未来增加新的南京南站情景，或把同一套方法用于别的公共治理案例，应该主要增加案例包，不重写项目、记录和确认机制。

## 已实现的 v0.2 基础层

`nanjing-south-hubcoord/` 已从单情景页面扩为平台原型：

- 首页展示四个模块：案例项目工作台、证据与边界库、协同实验室、案例叙事与复盘。
- 用户可新建本地演示项目，填写项目名称与当前研究问题。
- 已批准的模拟证据卡独立展示，并保留来源、定位、标签和模拟状态。
- SC-01 的协同议题卡可以归属到选定项目；生成与确认会进入该项目的活动记录。
- 所有原有边界继续生效：没有匹配规则时转人工；越权动作不能被包装成执行指令；所需主体未全部确认时，卡片不会变为“已确认”。

当前项目数据存于演示服务内存，服务重启后会重置。这是有意保留的 P0 限制，避免在尚未确定资料权限、账号和部署边界前，将研究信息写入长期存储。

## 后端分层

| 层 | 当前实现 | 后续职责 |
| --- | --- | --- |
| 案例包 | JSON 文件与 JSON Schema | 版本化、审核、装载不同案例包 |
| 规则引擎 | Flask 中的确定性校验 | 证据充分性、权限、人工确认、升级条件 |
| 项目服务 | `/api/v1/projects` | 项目、活动、后续研究笔记与导出任务 |
| 知识服务 | `/api/v1/knowledge/evidence` | 只向前端提供可展示的已审批卡片 |
| 协同服务 | `/api/v1/cards/*` | 生成和确认模拟协同议题卡，写审计记录 |

当前不调用大模型。下一步如引入模型，也只能放在规则引擎之后：模型可以协助归纳、提问和生成候选说明，不能自行决定权责、改变证据审批状态或发出外部行动。

## 前端工作台

平台首页不再只有“选择动作—出一张卡”。它按真实研究与教学的使用顺序组织：

1. 先建立或选择案例项目；
2. 查看哪些材料已经可以使用，以及为什么可以使用；
3. 进入情景推演，把生成的协同议题卡挂回项目；
4. 下一阶段从项目活动中整理案例叙事、反思和比赛交付物。

这种顺序避免把原始调研材料直接变成模型上下文，也使评委可以看到智能体如何受证据、规则与人工判断约束。

## 下一轮开发

### P1：案例研究工作流

- 项目持久化：SQLite 起步，保留迁移到 PostgreSQL 的接口。
- 项目内研究笔记：区分“研究者笔记”“已批准证据”“模拟设定”。
- 多情景管理：SC-02、SC-03 作为案例包中的可选情景，而非复制页面。
- 案例叙事模块：从已批准的证据链和活动记录生成可编辑提纲，并在段落旁标注来源。

### P2：受控智能体能力

- 检索只返回已批准且适用范围匹配的证据卡。
- 模型输出必须带证据引用、规则引用和不确定性说明；缺少依据时只提出待核验问题。
- 对高风险问题一律输出“需要人工复核”，不生成替代性的处置结论。
- 增加评价集：覆盖证据不足、角色越权、跨主体确认、数据边界和引用可追溯性。

### P3：比赛与教学交付

- 导出案例项目包：项目摘要、证据索引、情景推演、确认记录、研究反思。
- 教师模式与学生模式分开；学生只看必要材料，教师可审阅学习过程。
- 在资料权限和脱敏规则明确后，再决定是否启用多人账号与共享案例库。

## 现在的验收标准

平台不是“页面更多”就算完成。每加一个模块，至少要满足以下条件：

- 能说明它读的是什么资料，资料是否经过审批；
- 能说明它的输出是建议、模拟记录还是经过人工确认的结果；
- 能把过程挂回案例项目，而非只留在一次会话中；
- 不会因为模型生成而跳过权限、数据边界和人工确认。

这套标准沿用数字鲜笋把“角色知识包”和“研究档案”拆开的做法，但适配了公共治理案例中更关键的证据、权责与协同边界。
