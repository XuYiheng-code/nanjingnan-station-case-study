01 / Product decision

不是再做一个“会回答问题”的政务智能体

政务咨询、导办和数字人已相当普遍。南站案例真正稀缺的，不是再解释一遍办事流程，而是把跨红线、跨区、跨组织的事件协同过程做出来：谁发现、谁有权、谁确认、谁负责、缺什么数据，都必须留在同一条链上。

01 / CASE FIT

从“看得见、管不着”出发

南站的停车场、外围道路、铁路客流和属地秩序管理相互影响，但服务包、法定权力和数据系统并不天然统一。

02 / DIFFERENTIATION

把协同当作主产品

智能体输出的核心不是一段答案，而是一张可以进入联席沟通、人工确认和事后复盘的协同议题卡。

03 / SAFE BY DESIGN

建议与决定分开

模型只整理证据、识别权责边界、提出请求和风险提示。派单、执法、数据授权与责任确认始终由人完成。

02 / Case diagnosis

南站不是“技术没接上”，而是技术嵌在一组分散的权责关系里

条块和红线相互切割

场内停车、外围道路、不同广场及各条口的治理责任分属不同主体；一个拥堵事件往往跨越多个管理界面。

数据可以连通，不等于愿意共享

平台具备对接基础，但数据是否开放取决于用途、责任、成本和组织间信任，不是接口问题本身。

现场靠非正式协调兜底

节假日大客流、列车晚点等情形中，会议、电话和长期形成的配合仍是关键机制，且难以沉淀为可复用流程。

↔

协同官要补上的一段

不是取代已有的城市小脑、工单系统或联席会议，而是让它们之间少一层信息失真和责任悬空。

  • 把多源发现整理为同一事件证据包
  • 把“谁能做什么”明确写入权责地图
  • 把协同请求变成可确认、可拒绝、可升级的事项
  • 把结果沉淀成下一次可调用的案例与规则

它明确不解决什么

制度授权、部门预算、组织意愿和实体空间的现实约束不能被算法绕开。

  • 不替代行政执法或专业应急判断
  • 不强迫其他系统共享数据
  • 不以“最优解”代替多方协商
  • 不把演示数据伪装成实际运行成效
南站协同官是一个跨域枢纽事件的“协同副驾驶”：它将现场线索编译为有来源、有权限边界、有待确认事项的协同议题包，交由实际负责的组织和人员作出决定。

一句话边界：模型可以建议“找谁、凭什么、先确认什么”；模型不能决定“谁必须做、怎么执法、能否共享什么数据”。

03 / Experience design

一套产品，两种使用界面

比赛展示版把它做成可进入的案例教学与决策推演；未来试点版才服务于经授权的实际协同。两者共享规则和知识底座，但数据权限、操作范围、结果性质必须严格分开。

PRIMARY USER

交控万物现场主管

需要在权限有限的情况下，把现场发现、资源情况和协同请求迅速讲清楚，并留住对方确认过什么、拒绝过什么的记录。

04 / Agent workflow

从一条线索到一次可复盘的协同，不跳过任何责任节点

系统按“事件—证据—边界—请求—确认—复盘”运行。每一步都保留机器做了什么、人确认了什么、依据来自哪里。

STEP 01

事件归并

合并巡逻、传感器、市民上报、电话纪要和人工录入；先判断它们是否指向同一事件。

event_id · time · location · source
STEP 02

证据核验

标记每条线索的来源、时间与可信等级，区分“已证实”“待确认”“仅作风险提示”。

evidence_grade · trace_id
STEP 03

权责匹配

根据空间范围、事件类型、服务包和法定边界，列出可处置、需协同和不可越权的事项。

authority_map · boundary_flag
STEP 04

协同请求

生成最小必要的协同议题卡：请求谁做什么、为何需要、缺何种数据、何时确认。

request · owner · SLA · human_gate
STEP 05

回传与复盘

记录确认、拒绝、升级、结果和未解决原因；沉淀为案例知识和下一轮规则修订输入。

decision_log · outcome · lessons
05 / System architecture

技术架构的重点，是把“大模型”关进一套可追溯的制度壳里

语言模型只负责理解、检索、归纳和起草。事件是否成立、权责是否适用、协同是否发出，必须经过规则、证据和人工闸门共同约束。

RAG 不等于“说了算”

证据

检索结果只能说明某条依据或访谈如何表述。它不能自行推出新的授权关系，更不能把“可协商”写成“可指令”。

所有回答显示 source_id · quote_span · knowledge_version

规则优先于自由生成

边界

空间范围、服务事项、数据级别、协同对象和升级条件由结构化规则表判断；模型不得绕过红线标签。

if boundary_flag = restricted → require human confirmation

人的确认不可被静默跳过

责任

系统可预填请求、建议时限、生成会议提纲；真正发出、接收、升级或结案都要记录实际责任人。

actor_id · confirmation_time · decision_reason

演示数据与运行数据隔离

隐私

比赛展示只用脱敏、人工构造或经授权的材料；真实人员轨迹、车牌、旅客信息和敏感工单不得进入公开版本。

environment = demo | pilot · data_class = public | authorized
06 / Knowledge & rules

先建“知识与规则账本”，再接大模型

你们的一手调研材料是护城河，但不能整包丢给模型。要把访谈中的事实、判断、原话、未证实信息和研究者问题分开管理，并给每条材料一个可引用的位置。

资料类型可用层级进入系统的方式
访谈转录与会议纪要比赛 / 授权切为带说话人、时间段、主题和可信等级的证据卡。
服务合同、SOP、服务包授权抽取服务事项、空间范围、时段、升级路径和责任主体。
法律、政策与公开制度公开建立版本库；明确它们是边界依据而不是模型答案素材。
模拟事件与样例工单比赛人工编制、显著标注为模拟，用于交互和测试，不混入真实成效。
实时业务数据试点后只经责任单位书面授权接入；最小化字段、用途限定、日志可审计。

07 / Evaluation

展示效果不能代替评测。先测“有没有越界”，再测“有没有帮忙”

用 20 个由团队人工标注的典型情景组成测试集：其中至少包括铁路晚点、停车场外溢、红线内外车辆衔接、游商与秩序风险、积水和设备告警等情境。每一题都写清正确的证据范围、可行动作和必须人工确认的节点。

0越权行动建议不得把执法、行政命令或未授权数据调用写成系统可自动执行。
100%关键输出可溯源每个事实性结论都能回到材料编号、版本或人工录入记录。
≥90%权责路由正确率在人工金标准下，正确识别主责 / 协同 / 不可处理三类事项。
20情景红队测试覆盖数据缺失、依据冲突、边界不清和诱导越权等失败情形。
08 / Delivery plan

先把比赛版做得真实、稳定、可解释；再谈授权后的运行试点

目前到 9 月 7 日的目标不应是上线一个“真实指挥系统”，而是完成一个可访问、可演示、可复核的案例智能体。真实运行必须以合作协议、数据授权、操作规范和人工值守为前提。
